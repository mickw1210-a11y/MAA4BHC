# W03-04 设备异常退出与恢复

当前状态为待设计、待离线验证。Windows已有租约基础和崩溃复现。Mac已同步该源码，适合验证恢复判断及文件协议，Windows负责验证真实进程和命名互斥体行为。

先读[租约与持有者诊断](v04-device-lease.md)、[设备调用链](v04-device-call-chain.md)、[动作结果契约](v04-action-results.md)，再看 [device_lease.py](../../app/device_lease.py)、[action_result.py](../../app/action_result.py) 和 [test_device_lease.py](../../tests/test_device_lease.py)。

## 要解决的问题

合成场景中，项目副本 A 取得设备租约后异常退出。最后一个句柄关闭后，副本 B 可以新建同名互斥体。现有读取函数可以用给定的项目根定位对应日志，但 B 没有可靠机制发现 A 的记录，日志也只记录 acquired 与 release_requested。B 必须先判断旧持有者和上次动作，才能决定是否允许重新规划。重新取得租约只解决当前争用。

## 可立即开展的离线工作

- 复用实例身份、PID 与创建时间、动作 ID 及四类动作结果。用两个项目内的隔离目录和合成身份，复现 B 能取得新租约的模拟条件下，A 的未决记录仍须被识别。
- 比较把一份明确选定的项目内持久目录作为各副本共同使用的恢复位置，和由各副本保存、通过可信配置发现相应记录这两种候选。比较重点是新副本如何定位同一权威记录、首次使用如何与记录丢失区分、权限和路径失效如何处理、并发和重复恢复如何避免。用样例验证最有希望的方案。未经核实的目录遍历、项目外共享存储都不能作为现成依赖。
- 在设计及模拟执行器中约定提交前先保存可恢复的最小动作意图，保存失败时禁止发送。发送前后发生退出且无法证明调用是否到达设备，都按可能已提交处理。只有来自匹配实例的新观察足以核实结果时才关闭未决项。已有用户停止时保持停止。后续即使允许新操作，也须重新读取身份、画面及计划边界。
- 用模拟执行器实现并验证恢复入口所需的离线接口。W03-04 先验证恢复判断和记录协议。W03-07 负责接入设备派发，W03-08—09 再把意图写入和结果证据接到真实执行边界。恢复工作本身使用模拟提交，避免把真实派发作为本项的前置。

## 验收用例

| 场景 | 预期 |
| --- | --- |
| A 持有租约，B 同时启动 | B 不派发。持有者存活无法确认时，保留待核实状态。 |
| A 正常退出，有可验证的正常收尾记录 | B 能定位同一设备的权威记录。核对无未决动作后，恢复检查可以通过。 |
| A 异常退出，最后句柄关闭，B 随后启动 | 即使 B 拿到新锁，仍能定位 A 的持久记录并识别未决动作。 |
| 在写入意图、模拟发送、记录核实结果之间分别中断 | 写入意图失败时发送次数为零。可能已发送但无后置证据时停止，重启与重复检查均不得再发送原动作。 |
| 记录缺失、损坏、不可读、路径指向不同实例，或者 PID 被复用 | 缺少证据时保留待核实，旧 PID 的存活判断要核对创建时间。首次建立状态须走独立、明确的初始化分支。 |
| 取得匹配的新观察并核实上次结果 | 保留动作 ID、结果和证据引用。下一动作须重新规划并通过现行检查。 |

Mac 可用项目内临时目录、模拟进程状态和模拟执行器做用例。记录实际命令、结果、模拟发送次数及日志路径。Windows 用两个独立进程、不同副本路径及合成设备身份，至少复验活跃冲突、正常释放、最后句柄关闭、异常退出后的记录发现和未决动作处理。现有定向入口为 `python -W error::DeprecationWarning -m unittest discover -s tests -p test_device_lease.py`，把新增恢复测试的命令另记账本。先执行适用于当前改动的离线回归，再登记需要去 Windows 补的验证。

## 何时继续

Mac 验证完成可记“离线通过，待 Windows 复验”。W03-04 的恢复关口需等两副本 Windows 用例有证据后才通过，之后再开放 W03-07—12。所有设备入口接好并验证前，W04—W10 保持依赖受阻。

如果已验证的项目内方案无法提供所需的持久发现，记录失败场景、已排除方案及其证据。确需项目外存储时，先给出具体位置、数据、影响和替代方案，按项目规则确认。与此同时继续 [小游戏公开规则取证](minigame-rules/README.md)。新的有效证据优先于重复打开已查无结果的页面。
